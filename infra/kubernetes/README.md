# Kubernetes — подготовка к переносу

**На действующих VPS Kubernetes не установлен.** Владелец выбрал оставить рабочий
Docker Compose и подготовить будущий перенос. Оба текущих VPS: 1 vCPU / 2 ГБ.
K3s указывает для server минимум 2 CPU / 2 ГБ **без нагрузки приложения**:
[официальные требования](https://docs.k3s.io/installation/requirements).
Ресурсы приложения и PostgreSQL нужно добавить к этому минимуму.

Подготовлены Kustomize, namespace с Restricted Pod Security, ServiceAccount без
токена Kubernetes, Deployment, Service ClusterIP, PVC, probes и default-deny NetworkPolicy.
Образ намеренно требует замены, `replicas: 0`; применение набора не запускает бота.
Образ/секреты, база, внешний HTTPS и разрешения сети зависят от будущего кластера.

## До включения

1. Выбрать кластер и ресурсный запас; два небольших VPS не образуют отказоустойчивый
   control plane. Для HA нужна отдельная согласованная архитектура.
2. Подготовить PostgreSQL с проверенным восстановлением, закрытым подключением,
   отдельной ролью приложения и резервированием. База здесь намеренно не создаётся:
   новый пустой PostgreSQL не является переносом существующих клиентов/платежей.
3. Опубликовать проверенный образ в доступный кластеру registry, указать **digest**
   в Deployment. Подготовить `imagePullSecrets`, если registry закрытый.
4. Создать Secret `neyro-runtime` из закрытого файла (токен бота, DATABASE_URL,
   ключи провайдеров). Не копировать `.env` с административной ролью PostgreSQL
   и не коммитить Secret YAML. ConfigMap оставляет DEV_AUTH/бизнес/биллинг выключенными.
5. Выбрать StorageClass, перенести логотипы в PVC; UID/GID приложения 10001.
6. Подготовить HTTPS ingress и разрешить ему доступ к 8080. Настроить доверие
   прокси в FORWARDED_ALLOW_IPS для фактической сети, не использовать `*`.
7. Добавить правила DNS, PostgreSQL и исходящего HTTPS к Telegram/ИИ/ЮKassa.
   Нынешняя политика запрещает весь трафик: это намеренно незавершённая конфигурация
   до выбора сети. Проверить, что CNI действительно применяет NetworkPolicy.
8. Остановить и изолировать основной worker и поддержку, сверить публикации/оплаты
   после снимка, восстановить финальную базу. Только затем поднять **одну** реплику.
   Recreate не позволяет обычному обновлению запускать новую реплику до остановки
   старой; блокировка PostgreSQL дополнительно защищает от второго worker.
9. Бот поддержки переносится отдельно после проверки основного приложения.
   Проверить восстановление после отказа и маршрут отката перед сменой DNS.

```sh
kubectl kustomize infra/kubernetes > /tmp/neyro-k8s.yaml
# Только после выбора нужного kube-context и подготовки перечисленного выше:
kubectl diff -k infra/kubernetes
```

Набор ещё не был применён к реальному кластеру. Локально проверены только структурные
ограничения; рендер и schema validation включены в будущий GitHub CI.
[Правила Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/).
