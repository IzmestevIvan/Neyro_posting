# Mini App: VPN-dependent loading failure, 10 October 2026

The owner reported Telegram's native grey loading screen on multiple devices,
including the button in a fresh /start response. Changing the VPN exit restored
access. The failing exit IP is unavailable; the exact original network failure
has not been captured. This incident must not be described as a proven IP ban.

## Findings

All three HTTPS entry points answered successfully. The active app and database
were healthy, publications continued, and a signed bootstrap request for an
existing administrator returned HTTP 200 in 42 ms through the public domain.
The default Telegram menu URL was correct. Sampled proxy access logs contained
no HTTP 429 or 5xx. A browser without Telegram credentials correctly showed
an authentication error after loading the page.

All three hosts had only the SSH fail2ban jail; its actual nftables rules matched
TCP port 22, not HTTPS. Public TCP 80/443 were allowed. The Docker ingress chain
allowed established connections and published web ports. No VPN/geographic web
ban was found. No blanket unban or authentication change was performed.

TCP black-hole MTU recovery was disabled on all hosts and in Caddy's separate
network namespace. The proxy's five-second read-header deadline also limited
TLS setup. A VPN path dropping oversized packets and ICMP feedback can therefore
leave Telegram waiting before the application even loads.

## Reproduction and mitigation

An isolated three-namespace Linux test routed traffic through a 1200-byte path
with ICMP fragmentation feedback dropped. It used a locally generated test CA
certificate, a TLS client verifying that certificate and hostname, and a 64 KiB
response. No production interfaces or firewall rules were changed by the test.

- Without MTU recovery, TLS timed out and no response was received.
- Recovery alone still failed with a five-second TLS handshake deadline.
- Recovery with a fifteen-second deadline delivered all 65536 bytes in 6.59 s.

Host `net.ipv4.tcp_mtu_probing=1` is persisted by
`infra/ansible/ha-vpn-path-recovery.yml`; the live Caddy namespace is updated
without recreating the container. Compose also persists the setting for future
proxy recreation. Caddy's bounded read-header deadline is increased to 15 s.
Other limits and authentication remain in force.

Kernel setting semantics: https://www.kernel.org/doc/html/latest/networking/ip-sysctl.html

This mitigates a reproduced VPN path failure, but does not prove the original
exit failed for this reason. DNS filtering, a VPN provider's routing failure,
or inability to reach Telegram's external SDK can still require separate
investigation. Validation on a previously failing VPN is outstanding.

## Rollback

Restore the previous Caddyfile with the existing validate/reload/rescue playbook.
Restore the previous Compose file from its Ansible backup. Remove the dedicated
`91-neyro-vpn-path.conf` and return tcp_mtu_probing to 0 on hosts and the live
proxy namespace. Do not restart or restore the production database.
