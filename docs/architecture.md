# Архитектура

## Что это

Один Python-процесс, который одновременно держит:

- **long-polling бота** (aiogram) — карточки модерации, ручные посты, загрузка логотипа;
- **HTTP-сервер** (FastAPI + uvicorn) — REST и статика Mini App и отдельного веб-кабинета;
- **пять штатных циклов планировщика** — источники, обработка, публикация, дайджест и статистика;
- задачи сверки платежей, рассылок, журналирования ошибок и проверки блокировки единственного воркера.

Всё это живёт в одном event loop. Общее состояние — PostgreSQL (пул asyncpg на 8 соединений).

```
app/main.py                  точка входа: поднимает бота, сервер и циклы
├── bot/                     aiogram: хендлеры и карточки модерации
├── api/                     FastAPI: авторизация, REST, отдача мини-приложения
├── miniapp/                 панель, веб-кабинет, RU/EN и темы (vanilla JS, без сборки)
├── billing/                 каталог, заказы, подписки, платежи ЮKassa, чеки НПД
├── sources/                 откуда берётся контент
├── ai/                      Gemini: клиент, промпты, конвейер
├── core/                    фильтры, планировщик, публикация, водяной знак,
│                            промокоды, книга рекламодателей
├── config.py                чтение .env
└── db.py                    схема, миграции, обёртки над asyncpg
```

## Процессы

`app/main.py:run_service()` сначала получает PostgreSQL advisory lock единственного
воркера, затем запускает бота, HTTP-сервер и фоновые задачи. Второй экземпляр с той же
базой не начинает опрос Telegram или отправку постов. `scheduler.start(bot)` создаёт задачи:

| Цикл | Период | Что делает |
|---|---|---|
| `poll_loop` | `POLL_INTERVAL` (90 с) | обходит активные каналы и их источники, складывает новые посты со статусом `new` |
| `process_loop` | 1–10 с | до трёх каналов одновременно, по одному `new` на канал; свободные места пополняются без ожидания медленного запроса |
| `publish_loop` | 20 с | публикует `approved` с наступившим `publish_at`, собирает вечерний дайджест |
| `digest_loop` | отдельный цикл | подготовка вечерней сводки, не блокирует обычные отправки |
| `proposal_loop` | 5 мин, только при `BUSINESS_MODE_ENABLED=1` | бизнес-черновики; в текущем режиме задача не запускается |
| `stats_loop` | 30 мин | подписчики и средние просмотры, недельный отчёт, очистка старых строк |

Циклы обрабатывают ожидаемые ошибки внутри итераций. Если фоновая задача завершилась
неожиданно или потеряна блокировка воркера, `run_service()` отменяет остальные задачи.
Это не позволяет оставить HTTP-сервер работающим при остановленной обработке постов.
Сверка незавершённых платежей выполняется примерно раз в минуту, когда конфигурация
ЮKassa готова; неизвестный результат платежа не создаёт повторное списание.

## Поток данных

```
источник (t.me/s или RSS)
   │  poll_loop
   ▼
posts.status = 'new'
   │  process_loop
   ├─ стоп-слова, «только с медиа», «только хиты»  ──► 'filtered'
   ├─ дедуп по Жаккару                             ──► 'duplicate'
   ├─ регулярки рекламы                            ──► 'filtered'
   ├─ ИИ: триаж → рерайт → фактчек                 ──► 'filtered' при провале
   ▼
автопостинг? ──да──► 'approved' + publish_at ──► publish_loop ──► 'published'
             └─нет─► 'pending' в Mini App ──► ручное одобрение ──► 'published'
```

## Мультиарендность

У каждого канала есть `owner_id`. Каждый обработчик API проходит через
`auth.owned_channel()`, который сравнивает владельца с текущим пользователем.
Администраторы из `ADMIN_IDS` видят сводку по всем каналам через `/api/admin/*`.

Дневной лимит постов считается **на владельца**, а не на канал: `publisher.quota_left()`
складывает публикации по всем каналам пользователя за текущие сутки UTC.

## Доступ

`auth.current_user` проверяет `initData` Telegram Mini App, а `auth.active_user`
дополнительно требует действующий доступ от подписки, промокода или администратора.
Отсутствие доступа даёт 402; профиль и экран доступа остаются доступны.

Веб-кабинет `https://flipbazar.ru/account` использует отдельный Telegram OIDC Login:
подпись RS256, issuer/audience, срок и одноразовый nonce проверяются сервером.
Непрозрачная cookie-сессия `Secure`, `HttpOnly`, `SameSite=Lax` действует сутки;
в базе хранится её хеш. Изменения требуют точного Origin и CSRF-токена.
Mini App не может создать платёж через initData: изменение подписки и checkout
принимают только сессию самостоятельного кабинета.

Каталог содержит PLUS, PRO, EXPERT, CREATOR, UNLIMITED. Суммы хранятся в копейках,
расчёт фиксируется на 10 минут, заказ записывается до запроса к ЮKassa.
Доступ выдаётся только после серверной проверки платежа, а не по возврату пользователя
на страницу успеха. Повторные webhook и запросы не должны выдавать период второй раз.
Тестовые платежи не дают боевого доступа. [Подробности биллинга](billing.md).

## Развёртывание и интерфейс

Основной Docker-стек: `app`, `support`, `db`, `caddy`. Caddy принимает HTTPS;
приложения работают с ограниченным пользователем PostgreSQL и закрытыми сетями.
Резервный сервер хранит копии и мониторит основной; его нельзя считать вторым активным
воркером или автоматическим failover без отдельной процедуры переключения.

`preferences.js` хранит выбор RU/EN и system/light/dark в localStorage. Перевод
помеченных подписей и динамических интерфейсных строк не изменяет посты, инструкции
пользователя и `channels.lang`. Учебник в `app.js` содержит восемь двуязычных тем,
сохраняет прогресс и открывает разделы без отправки постов или изменения настроек.
Бизнес-режим отключён на сервере и в интерфейсе; старые данные не удаляются.

## Почему один процесс, а не микросервисы

Продукт рассчитан на десятки каналов на одном сервере с 1 vCPU. Вся работа — сетевая:
ожидание t.me, Gemini и Telegram API. Один event loop с этим справляется. Узкое место
появится не в архитектуре, а в квотах Gemini.

Обработка ограничена тремя одновременно занятыми каналами; один канал защищён
блокировкой. Публикация использует отдельные слоты. Вызовы ИИ дополнительно
ограничены четырьмя HTTP-слотами и блокировкой на ключ. Медленный или недоступный
провайдер всё ещё может приводить к задержкам и истечению срока новостей.

Изменения аудита 16 сентября и их статус проверки описаны в
[editorial-audit-2026-09-16.md](editorial-audit-2026-09-16.md). Не считать локальные
исправления уже установленными на сервере до отметки о выкладке.
