# Управление серверами и инцидентами

Ansible управляет двумя существующими Ubuntu 24.04 VPS: primary `31.76.244.26`
и reserve `144.31.53.148`. Основной сервер — единственный активный бот. Резерв
принимает зашифрованные копии, проверяет восстановление и наблюдает сайт снаружи.
Это не кластер с автоматическим выбором лидера. Kubernetes пока не запускается.

## Применение и проверка

```sh
ansible-galaxy collection install -r infra/ansible/requirements.yml
make ansible-check
make ansible-apply
make ops-status
```

Используется существующий SSH-ключ `~/.ssh/neyro_deploy`, проверка host key обязательна.
Ansible последовательно меняет серверы. Повторный прогон должен показывать `changed=0`;
обновление apt cache со временем может дать самостоятельное изменение.
Не используйте `--diff` с произвольными секретными задачами: штатные задачи credentials
имеют `no_log`. Ключи, пароли и Telegram token не хранятся в Git или inventory.

Структура:

- `site.yml` — базовые службы, SSH, обновления, release-инструменты.
- `tasks/security.yml` — UFW, защита Docker ingress, Fail2ban, sysctl, auditd.
- `tasks/operations.yml` — мониторинг, безопасные команды управления, уведомления.
- `tasks/reserve.yml` — скрипты резервирования и таймеры; рабочие боты не запускаются.
- `operations.yml` — явные эксплуатационные операции, по умолчанию только статус.

## Что контролируется

| Область | Основной сервер | Резерв |
|---|---|---|
| Входящие соединения | TCP 22, 80, 443 | TCP 22 |
| Docker published ports | Только внешние TCP 80/443 | Внешний Docker ingress запрещён |
| SSH | Только ключи, root без пароля, ограничение попыток | Аналогично |
| Подбор SSH | Fail2ban, 4 ошибки / 10 мин, блокировка от часа до суток | Аналогично |
| Обновления ОС | Ежедневные security updates, без автоматического reboot | Аналогично |
| Аудит | Изменения identity, SSH, firewall, systemd и operations config | Аналогично |
| Логи | journald 128 MiB, audit до 4 × 16 MiB с ротацией | Аналогично |
| Мониторинг | Каждую минуту: контейнеры, БД, память, диск/inode, защитные службы | То же + отсутствие рабочих ботов, таймеры |
| Внешняя проверка | Наблюдается резервом | HTTPS основного сервера и свежесть копии |
| Копии | Экспорт только через ограниченный SSH-ключ, age encryption | Каждые 15 минут; отдельная пробная БД, хранение 7 дней |

Docker-трафик может обходить UFW INPUT. Поэтому отдельная служба устанавливает
собственную цепочку `NEYRO-INGRESS` в `DOCKER-USER`, ограничивая только входящий
forwarded traffic с внешнего интерфейса. Внутренний обмен контейнеров и ответы на
исходящие запросы сохраняются. Правила загружаются атомарно через iptables-restore
и повторяются при перезапуске Docker. Монитор проверяет состав правил и подключение
цепочки; повторный Ansible исправляет обнаруженное расхождение; IPv6 обрабатывается, если его Docker-chain существует.
[Ansible UFW](https://docs.ansible.com/projects/ansible/latest/collections/community/general/ufw_module.html),
[Ansible sysctl](https://docs.ansible.com/projects/ansible/latest/collections/ansible/posix/sysctl_module.html).

Audit фиксирует факт изменения, а не содержимое secret-файлов. Не ведётся запись
всех аргументов процессов: там могут оказаться токены. Хостовые журналы остаются
локальными; после полного захвата root они не являются защищённым внешним архивом.

## Как реагирует автоматизация

1. Первые две неудачные проверки не отправляют тревогу. На третьей администраторы
   получают Telegram. Напоминание — не чаще раза в час на получателя; восстановление
   тоже сообщается. Недоступность одного получателя не вызывает повторы другим.
2. Только `app` на primary может быть перезапущен автоматически: он должен оставаться
   running, но unhealthy три проверки подряд. БД, память, диск и защитные службы
   должны быть в норме. Stopped/restarting/unknown контейнер не запускается.
3. Не более двух попыток в час и не чаще одной в 15 минут. Попытка сохраняется до
   выполнения, поэтому прерванная команда тоже расходует лимит.
4. Общий lock исключает одновременный restart, выпуск и fencing. Перед действием
   состояние проверяется заново. `maintenance`, `FENCED` и признак reserve запрещают
   автоматическое восстановление. БД, Caddy, support не перезапускаются этим механизмом.
5. Docker уже имеет собственную restart policy для аварийного завершения рабочих
   контейнеров. Монитор дополняет её для зависшего HTTP-приложения. Логи содержат
   `app_restart_requested` или `app_restart_failed`; последующие проверки подтверждают
   здоровье. Это не обещание автоматического исправления любой ошибки.

Состояние без секретов: `/var/lib/neyro-ops/status.json`. Счётчики восстановления:
`recovery.json`. Ключ уведомлений: `/etc/neyro-ops/alerts.json`, root:root 0600.
Первоначально он берётся Ansible с существующего резерва, как разрешил владелец.

## Процедуры администратора

```sh
export ANSIBLE_CONFIG=infra/ansible/ansible.cfg
# Статус обоих серверов, без записей/уведомлений/восстановления:
ansible-playbook infra/ansible/operations.yml
# Дополнительная копия с пробным восстановлением:
ansible-playbook infra/ansible/operations.yml --limit reserve -e operation=backup
# Обслуживание запрещает автоматическое восстановление и CD:
ansible-playbook infra/ansible/operations.yml --limit primary -e operation=maintenance_on
ansible-playbook infra/ansible/operations.yml --limit primary -e operation=maintenance_off
# Осознанный перезапуск уже работающего app при здоровой БД:
ansible-playbook infra/ansible/operations.yml --limit primary -e operation=restart_app
```

В maintenance проверки app/support/proxy подавлены, но само затянувшееся обслуживание
показывается отдельной тревогой. Резерв продолжает сообщать о внешней недоступности.
Не включайте maintenance для штатного CD: выпуск сам держит общий lock.

При инциденте сначала получить статус, проверить `journalctl -u neyro-ops.service`,
`systemctl --failed`, журнал нужного сервиса. Не публиковать полные Docker inspect,
env-файлы и необработанные журналы в чат/issue. `ops-status` выводит только безопасные поля.

- Нет места/памяти: выяснить источник, остановить рост, не удалять копии и базу вслепую.
- БД нездорова: сохранить диагностику, оценить диск и целостность; автоматического
  рестарта/отката БД нет, чтобы не усугубить потерю данных.
- Ошибка релиза: проверить release status, штатный CD возвращает код и оба старых
  образа, если новая версия не проходит проверку. Базу автоматически не откатывает.
- Подозрение на захват: закрыть доступ на уровне провайдера, сохранить свидетельства,
  отозвать затронутые ключи, восстановить чистый узел. Ansible не доказывает, что
  скомпрометированный root стал снова доверенным.
- DDoS: локальные лимиты не спасут переполненный канал VPS; нужна фильтрация перед ним.

## Аварийный резерв и защита от двух активных ботов

```sh
# Останавливает app/support primary и отключает их restart policy.
# Выполнять только при решении переключаться; это намеренный перерыв работы.
ansible-playbook infra/ansible/operations.yml --limit primary -e operation=fence_primary
# Заменяет только dormant БД резерва, сохраняет encrypted snapshot, останавливает расписания:
ansible-playbook infra/ansible/operations.yml --limit reserve \
  -e operation=prepare_reserve -e replace_dormant_reserve=true
```

После fencing первичный сервер остаётся заблокирован для CD и recovery даже после
перезагрузки; `maintenance_off` не снимает `FENCED`. Если SSH primary недоступен,
его необходимо выключить в панели провайдера и убедиться в остановке. Таймаут сети
не доказывает, что бот перестал публиковать.

Подготовка резерва не открывает HTTP-порты, не меняет DNS и не запускает workers.
Перед активацией вручную сверить публикации после времени снимка, платежи и очередь;
восстановленные каналы остаются paused, рассылки — recovery_hold. Дальше применять
[план восстановления](disaster-recovery.md). Возврат на primary требует отдельного
плана синхронизации данных и проверки единственного активного сервера.

## Оставшиеся границы

Ansible не заменяет внешнюю L3/L4 Anti-DDoS, управление аккаунтом хостинга/DNS и MFA
провайдера. SSH пока доступен из интернета по ключу; VPN/bastion и список администраторских
IP не настроены. Резерв находится у того же поставщика: сбой его панели/сети может
затронуть оба VPS. Нет immutable offsite-хранилища, внешнего SIEM/EDR или третьего
наблюдателя. При падении обоих узлов Telegram-уведомление от них прийти не сможет.

Копия раз в 15 минут означает возможную потерю новых данных после последнего успешного
снимка; порог тревоги по возрасту — 30 минут. Это контролируемый холодный/тёплый резерв,
не синхронная репликация и не автоматическое переключение DNS.
