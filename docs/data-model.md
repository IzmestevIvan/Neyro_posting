# Модель данных

PostgreSQL 16. Схема — `app/db.py:SCHEMA`, доступ — через тонкие обёртки над asyncpg:
`fetch_all`, `fetch_one`, `execute`, `insert` (возвращает новый id), `update` (возвращает
число изменённых строк).

Все запросы в коде написаны с плейсхолдерами `?`; `db._convert()` переписывает их в
`$1…$n` перед отправкой. Это позволило перенести приложение с SQLite, не переписывая
каждый вызов.

`insert()` существует отдельно от `execute()` потому, что не у всех таблиц есть колонка
`id` — `users`, `kv` и `stats_daily` ключуются иначе, и слепое `RETURNING id` ломало бы их.

## users

Владелец панели. Создаётся при первом `/start` или первом открытии мини-приложения.

| Колонка | Тип | Смысл |
|---|---|---|
| `tg_id` | INTEGER PK | Telegram ID |
| `username`, `first_name` | TEXT | для отображения в админке |
| `is_admin` | INTEGER | 1, если ID есть в `ADMIN_IDS` на момент создания |
| `blocked` | INTEGER | 1 — API отдаёт 403 на любой запрос |
| `daily_limit` | INTEGER | публикаций в сутки на всего владельца |
| `max_channels` | INTEGER | сколько каналов разрешает тариф |
| `access_until` | TIMESTAMPTZ | до какого момента открыта панель; пусто — доступа нет |
| `promo_code` | TEXT | каким кодом активирован доступ |

## promo_codes

Панель работает только по приглашению. Код выпускается в админ-панели и несёт тариф:

| Колонка | Смысл |
|---|---|
| `code` | вида `ABCD-2345`; из алфавита убраны `O`, `I`, `0`, `1`, чтобы код можно было продиктовать |
| `plan` | `start` / `pro` / `unlim` — пресеты в `app/core/promo.py:PLANS` |
| `daily_limit`, `max_channels`, `days` | что именно код выдаёт |
| `used_by`, `used_at` | кто активировал; повторно другим человеком код не примется |
| `note` | комментарий администратора: кому и за что выдан |

Повторный ввод **своего** кода не меняет срок и лимиты. Только новый код добавляет
срок от текущей даты окончания (или от текущего момента, если доступ истёк). Активация
блокирует строки пользователя и кода в одной транзакции; два получателя не могут
одновременно использовать один код. Администраторы из `ADMIN_IDS` проходят без кода всегда.

## channels

Канал назначения. `chat_id` заполняется через `bot.get_chat()` при добавлении — если бот
не админ канала, добавление падает с понятной ошибкой и строка не создаётся.

Настройки публикации: `autopost`, `paused`, `delay_mode`, `pace`, `tz`,
`window_start`, `window_end`.

Настройки контента: `quality`, `instructions`, `stopwords`, `lang`, `channel_voice`,
`hits_only`, `media_only`, `digest_enabled`, `digest_time`, `digest_sent_on`.

Оформление: `signature_text`, `signature_url`, `watermark`, `logo_path`.

Прочее: `gemini_key` (ключ клиента, пусто — общий серверный), `voice_sample`
(до пяти постов самого канала, подтягиваются при включении «Голоса канала»).

Важно: `window_start` валидируется в диапазон 0–23, `window_end` — 1–24.
`datetime.replace(hour=24)` бросает `ValueError`, поэтому 24 как **начало** окна запрещено.

## sources

| Колонка | Смысл |
|---|---|
| `kind` | `tg` (публичное превью t.me) или `rss` |
| `ref` | username канала без `@` либо адрес ленты |
| `median_views` | медиана просмотров последних постов, пересчитывается при каждом опросе; база для фильтра «только хиты» |
| `last_uid` | последний виденный пост; от него отсчитываются новые |
| `error` | текст последней ошибки опроса; в панели такой источник подсвечивается красным |

Уникальность — `(channel_id, kind, ref)`, один и тот же донор нельзя добавить дважды.

## posts

Центральная таблица. Жизненный цикл поста задаётся полем `status`:

| Статус | Значение | Кто ставит |
|---|---|---|
| `new` | скачан из источника, не обработан | `poll_source` |
| `pending` | переписан, ждёт решения владельца | `process_post` без автопостинга |
| `approved` | одобрен, ждёт своего времени в `publish_at` | `process_post` с автопостингом |
| `digest` | короткая новость, отложена в вечернюю сводку | `process_post` при включённом дайджесте |
| `publishing` | захвачен на отправку прямо сейчас | `publish_post` |
| `published` | ушёл в канал, есть `message_id` | `publish_post` |
| `duplicate` | совпал с уже виденным | дедуп |
| `filtered` | отсеян стоп-словом, фильтром, рекламной эвристикой или ИИ | фильтры и конвейер |
| `rejected` | владелец нажал ❌ | бот или API |
| `failed` | не удалось опубликовать `MAX_ATTEMPTS` раз | `publish_post` |

Статус `publishing` существует ради атомарного захвата: панель и карточка в чате могут
одобрить один пост одновременно, а между проверкой статуса и отправкой есть `await`.
`publish_post` делает `UPDATE ... WHERE status IN (...)` и смотрит на число изменённых
строк — выигрывает ровно один вызов, второй получает `AlreadyPublished`.

Прочие важные поля:

- `uid` — идентификатор в источнике (`moscowach/42987` или GUID из RSS). Защищает от
  повторного скачивания того же поста.
- `fingerprint` — отсортированный набор основ слов, по нему считается дедуп.
- `media` — JSON-массив. Элемент либо `{"type","url"}` (ссылка из источника), либо
  `{"type","file_id"}` (медиа, присланное боту в чат). URL файла Telegram **не хранится**:
  он содержит токен бота.
- `attempts` — счётчик неудачных отправок, на `MAX_ATTEMPTS` пост уходит в `failed`.
- `mod_message_id` — сообщение с карточкой; по нему находится пост, когда владелец
  отвечает на карточку правкой.

## ad_offers

Реклама, отсеянная из источников. Идея простая: рекламодатель, который регулярно
появляется в ваших донорах, уже платит за охват в вашей нише — с ним имеет смысл
работать напрямую.

| Колонка | Смысл |
|---|---|
| `advertiser` | вытащенное из текста имя: `ООО «…»` либо @-упоминание |
| `contacts` | JSON-список: t.me-ссылки, @-логины, почта, телефоны |
| `score`, `reasons` | сколько баллов набрал рекламный фильтр и за что |
| `seen_count`, `last_seen_at` | сколько раз это же предложение встречалось |
| `status` | `new` → `contacted` → `archived` |
| `fingerprint` | тот же набор основ слов, что и у постов |

Повтор той же рекламы не плодит записи: при сходстве по Жаккару ≥ 0.5 инкрементируется
`seen_count`. Порог здесь выше, чем у дедупа постов (0.33) — одинаковые рекламные
креативы совпадают почти дословно, и лишняя строгость защищает от склейки разных
рекламодателей с похожей лексикой.

## stats_daily

Ключ `(channel_id, day)`, день — в UTC. Счётчики `published`, `filtered`, `duplicates`,
`ai_requests` накручиваются в момент события, `subscribers` и `avg_views` обновляются
раз в полчаса по `MAX` (в пределах суток значение не уменьшается).

Эта таблица — **источник правды для пожизненных чисел** в панели. Строки `posts`
чистятся (см. ниже), а `stats_daily` крошечная и живёт вечно, поэтому «опубликовано»,
«дубликаты» и «отфильтровано» считаются именно отсюда.

## kv

Служебные значения: `next_slot:<channel_id>` (равномерный темп), `active:<tg_id>`
(последний выбранный канал), `main_model_cooldown_until`, `last_publish_at`,
`weekly_report_on`, `pruned_on`.

## Очистка

`scheduler.prune_posts()` раз в сутки удаляет:

- `filtered` / `duplicate` / `rejected` / `failed` старше **14 дней**;
- `published` старше **90 дней**.

Дедуп смотрит на последние 200 постов с непустым `fingerprint`, так что окна хватает.
Счётчики при этом не страдают — они в `stats_daily`.

## Миграции

`CREATE TABLE IF NOT EXISTS` не трогает уже существующую таблицу, поэтому каждая колонка,
добавленная после первого релиза, обязана быть **и в `SCHEMA`, и в списке `MIGRATIONS`**
в `app/db.py`. При старте `_apply_migrations()` сверяет `information_schema.columns` и
делает `ALTER TABLE ADD COLUMN` для недостающих. Операция идемпотентна.

Забыть про этот список — самый лёгкий способ уронить прод: код обратится к новой колонке,
а в боевой базе её нет. Тест `tests/test_migrations.py` воспроизводит ровно этот сценарий.

## Переезд с SQLite

`scripts/sqlite_to_pg.py` переносит старую базу:

```bash
docker compose exec -T app python -m scripts.sqlite_to_pg /app/data/legacy.db
```

Скрипт приводит текстовые даты к `timestamptz`, вставляет всё с `ON CONFLICT DO NOTHING`
и в конце выставляет счётчики последовательностей по максимальным `id`. Без `--force` он
не тронет таблицу, в которой уже есть строки.

**Важно про снимок SQLite.** В режиме WAL файл `neyro.db` может быть почти пустым: данные
лежат в `neyro.db-wal`. Простое копирование `.db` теряет всё. Корректный снимок —
`VACUUM INTO 'copy.db'` либо `.backup`.
