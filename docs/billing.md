# Оплата и личный кабинет

> Текущее состояние 3 октября: интерфейс и код выпущены, новый ключ подтверждён.
> Создание оплаты временно выключено из-за повторных TLS-таймаутов с VPS к ЮKassa.
> Контрольного списания ещё не было. [Диагностика](yookassa-connectivity.md), [передача проекта](HANDOFF.md).

Документ описывает текущий код, а не подтверждение готовности действующего магазина. Личный кабинет находится по адресу `PUBLIC_URL/account`. Оплата создаётся только из обычного браузера после входа через Telegram. Mini App читает полученный доступ; платёжные операции требуют отдельной браузерной сессии.

## Тарифы и учёт

Источник цен — `app/billing/plans.py`. Суммы хранятся целыми копейками.

| Тариф | За календарный месяц | Общий дневной лимит постов |
| --- | ---: | ---: |
| PLUS | 390 ₽ | 5 |
| PRO | 490 ₽ | 10 |
| EXPERT | 590 ₽ | 15 |
| CREATOR | 990 ₽ | 25 |
| UNLIMITED | 1 490 ₽ | 50 |

Лимит общий для всех каналов одного Telegram-аккаунта. Название UNLIMITED не отменяет ограничение в 50 постов. Сутки меняются в 00:00 UTC, то есть в 03:00 по Москве. Смена тарифа не обнуляет уже использованный дневной объём.

Фактический счётчик — публикации и зарезервированные отправки в `delivery_attempts`, включая отправки с неизвестным результатом. Однозначно неудавшаяся отправка освобождает резерв. Генерация черновика и отдельный запрос к модели сами по себе этот счётчик не увеличивают. Количество подключаемых каналов остаётся отдельным ограничением `users.max_channels`; каталог оплаты его не меняет.

Новый оплаченный период начинается после подтверждения успешного платежа. Месяц означает соответствующую дату следующего месяца с ограничением по последнему дню: например, 31 января → 28/29 февраля. Автоматического продления и сохранения платёжного способа в коде нет.

## Повышение, снижение и продление

Повышение применяется после оплаты. Доплата равна разнице месячных цен, умноженной на долю оставшегося времени текущего периода. Округление вверх до копейки, минимум 1 ₽. Дата окончания периода сохраняется. Расчёт действует десять минут; сервер проверяет принадлежность пользователю и версию подписки.

Снижение лишь сохраняет выбор следующего тарифа: сейчас сумма равна нулю, деньги не списываются, текущий лимит не уменьшается. После окончания периода пользователь должен вручную оплатить выбранный тариф. Сам запланированный выбор не предоставляет доступ. Если нет другой действующей подписки или доступа по коду, после окончания оплаченного периода доступ прекращается.

Текущий тариф можно вручную оплатить на следующий месяц заранее. Новый период включается на границе периодов. При уже оплаченном будущем периоде повторное продление и снижение требуют сверки с поддержкой. Повышение текущего периода не меняет тариф уже оплаченного будущего периода: эти даты и тарифы нужно проверить отдельно в кабинете.

Доступ по ранее выданному коду сохраняется как отдельное прежнее право с исходной датой окончания; время по коду не ставится на паузу. Во время оплаченной подписки действует её лимит. После неё прежнее право восстанавливается только в пределах его исходного срока. Новый код нельзя активировать поверх оплаченного текущего/будущего периода или незавершённого платежа.

## Настройка сайта и Telegram

Используйте поля из `.env.billing.example`. В нём нет ключей и включённой оплаты. Приложение читает окружение и основной `.env`; отдельный `.billing.env` автоматически не подключается. В Docker `scripts/render-app-env.sh` формирует `.app.env` из серверного `.env`, а контейнер использует `.app.env`.

1. Укажите `PUBLIC_URL` как HTTPS-origin без пути, например `https://example.com`. Страница кабинета будет `https://example.com/account`.
2. В BotFather откройте нужного бота → **Login Widget** → **Allowed URLs** и зарегистрируйте origin сайта. Telegram требует также регистрировать конкретные redirect URI при использовании redirect-flow. Текущий код использует popup `Telegram.Login.auth`, поэтому отдельного `/auth/callback` здесь нет. [Telegram Login](https://core.telegram.org/bots/telegram-login).
3. Перенесите выданный Client ID в `TELEGRAM_LOGIN_CLIENT_ID`. Оставьте алгоритм подписи RS256. Вход проверяет ID token на сервере и связывает его с одноразовым nonce. Client Secret OIDC этот вариант интеграции не использует; в браузер его передавать не нужно.
4. Проверьте реальный вход на `/account` тем же Telegram-аккаунтом, который используется в боте. Для popup не должен применяться `Cross-Origin-Opener-Policy: same-origin`; допускается `same-origin-allow-popups`. [Требования Telegram к popup](https://core.telegram.org/bots/telegram-login).

Для локальных тестов вход и API провайдера подменяются. Публичный вход Telegram, cookie на рабочем HTTPS-домене и защитные заголовки требуют отдельной интеграционной проверки.

## Настройка ЮKassa и чеков

Для запрошенной контролируемой проверки используется существующий **LIVE-магазин**, а не вновь созданный тестовый магазин. `YOOKASSA_ENV=live` требует ключ с префиксом `live_`; операции оплаты в таком окружении используют реальные деньги. Само заполнение конфигурации или запуск тестов оплату не создаёт.

Заполните `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` в защищённом окружении. Не переносите ключ в документацию, репозиторий, браузер или вывод диагностики. Токен провайдера из BotFather Payments не является секретным ключом API ЮKassa. [Аутентификация ЮKassa](https://yookassa.ru/developers/using-api/interaction-format).

Владелец подтвердил статус самозанятого. Для него используется `YOOKASSA_RECEIPT_MODE=npd_manual`: в запрос оплаты не добавляется чек 54-ФЗ. Email покупателя сохраняется вместе с неизменяемым заказом для выдачи чека. Самозанятый регистрирует доход и формирует чек в «Мой налог»; автоматический выпуск чеков НПД через ЮKassa недоступен. Это не схема НДС 0%: для самозанятого применяется «Без НДС». [Правила чеков ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/basics), [ФНС о НПД](https://npd.nalog.ru/).

В `/account` администратор видит оплаченные заказы, ожидающие чека, email, сумму и назначение. Создайте фактический чек в «Мой налог», сверьте его с заказом и прикрепите прямую ссылку вида `https://lknpd.nalog.ru/api/v1/receipt/…/print`. Она появится в истории оплат покупателя. Автоматической отправки чека по email и автоматической регистрации дохода в ФНС здесь нет. Проверка ссылки ограничена безопасным официальным адресом: приложение не проверяет содержимое чека в ФНС. При возврате необходимо отдельно проверить аннулирование/корректировку в «Мой налог»; административный список возвратов служит напоминанием, а не подтверждением выполнения.

Подтверждённое получение денег ставит заказ в очередь чеков даже при ручной сверке доступа. Ошибочные или непроверенные уведомления такую запись не создают. Дубликаты уведомлений не добавляют новые периоды и не стирают прикреплённый чек.

Альтернативный режим `yookassa_54fz` требует подтверждённых `YOOKASSA_VAT_CODE` (1–12), `YOOKASSA_PAYMENT_SUBJECT` (`service` либо `intellectual_activity`) и `YOOKASSA_PAYMENT_MODE=full_payment`. В нём email и позиция чека передаются ЮKassa. `full_prepayment` заблокирован, поскольку отдельный чек зачёта предоплаты не реализован. `tax_system_code` явно не передаётся. [Параметры 54-ФЗ](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/other-services/parameters-values).

`YOOKASSA_FISCAL_READY=1` подтверждает выбранный порядок чеков; это не автоматическая проверка налоговой регистрации или кассы.

В настройках уведомлений магазина укажите `https://example.com/api/billing/webhook`, заменив домен на `PUBLIC_URL`, и события `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`, `refund.succeeded`. Уведомление служит сигналом для повторного чтения объекта через авторизованный API. При зачислении сверяются ID заказа, пользователь, магазин, окружение, валюта, сумма и итоговый статус. Возвращение браузера на `/account?order=…` само по себе доступ не выдаёт.

`BILLING_ENABLED=1` разрешает создание оплаты только вместе с заполненными параметрами магазина и фискализации. Пока они не подтверждены, оставьте `BILLING_ENABLED=0` и `YOOKASSA_FISCAL_READY=0`.

## Проверки без списаний

Тесты `tests/test_billing.py` используют `httpx.MockTransport`, локальную базу `neyro_test` и вымышленные ключи. Даже сценарии с названием `live` не обращаются в магазин и не списывают деньги. Тесты очищают только выделенную локальную тестовую базу; её URL проверяется перед запуском.

```sh
TEST_DATABASE_URL=postgresql://neyro@127.0.0.1:55439/neyro_test \
  .venv/bin/python -m pytest -q tests/test_billing.py tests/test_account_auth.py
```

Команда предполагает уже запущенную отдельную локальную базу на указанном порту. Данные рабочего PostgreSQL для неё использовать нельзя. В отдельном тестовом магазине ЮKassa окружение `test` также не выдаёт реальный доступ: подтверждённый платёж получает статус `test_succeeded`.

## Контролируемая проверка действующего магазина

Реальный проход ещё не считается подтверждённым результатами локальных тестов. Перед ним должны быть заполнены налоговые параметры и завершены настройка входа, уведомлений и HTTPS. Владелец проверяет в своём обычном браузере выбранный тариф, точную сумму и email чека; подтверждение на платёжной странице выполняется самим плательщиком.

После одной согласованной оплаты сверяют один платёж в кабинете ЮKassa, один заказ в приложении, чек и один оплаченный период. Затем проверяют отображение тарифа в `/account` и Mini App, общий счётчик по нескольким каналам и отсутствие повторного заказа после обновления страницы. Возврат, если он требуется для контрольного платежа, является отдельной денежной операцией и проводится осознанно с последующей сверкой.

Нельзя считать интеграцию проверенной только по наличию ключа, созданной ссылке оплаты или возврату браузера. Результат live-проверки, ID заказа без секретов, сумма и статус чека фиксируются после фактического прохождения.

## Сверка, возвраты и ручное рассмотрение

Заказ сохраняется до обращения к провайдеру. Повторные запросы используют тот же ключ идемпотентности; одновременно допускается один незавершённый заказ на аккаунт. Если неизвестный результат создания не удалось восстановить за 23 часа, заказ передаётся на проверку вместо повторного создания платежа за пределами гарантированного окна. ЮKassa гарантирует идемпотентность в течение 24 часов. [Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format).

Фоновая сверка запускается каждую минуту; она также активирует будущие оплаченные периоды и завершает истёкший доступ. Проверка состоявшихся оплат и чеков выполняется отдельно. `BILLING_ENABLED=0` останавливает обращения к провайдеру, но локальная смена оплаченных периодов продолжает работать.

Возвраты поступают из подтверждённых уведомлений ЮKassa. Полный возврат самостоятельного обычного платежа отзывает связанный период. Частичные возвраты, возвраты доплат, связанные повышения тарифа, расхождения чеков и уже оплаченные будущие периоды требуют операционной сверки. У приложения нет готового интерфейса разрешения таких спорных случаев или автоматического создания возврата.

При `review` у заказа или `needs_review` у аккаунта сначала сравните заказ, сумму, подтверждённые возвраты и связанные периоды с кабинетом ЮKassa. Не удаляйте заказ и не снимайте блокировку лишь ради повторной оплаты. Решение должно учитывать всю цепочку исходной покупки, доплат и будущих периодов; после него отдельно проверяются права доступа и журнал событий.

До публичного запуска остаются интеграционные проверки действующего магазина, налоговой схемы, реального чека, Telegram-входа, возвратов и границы заранее оплаченного периода. Локальные проверки кода не подменяют эти проверки.

## Выпуск интерфейса, НПД и текущая блокировка 3 октября 2026

Новый предоставленный владельцем ключ проверен чтением `GET /v3/me`: HTTP 200, магазин 1414485, `test=false`, `status=enabled`, `fiscalization_enabled=false`. Создание платежа при этой проверке не выполнялось. Client ID Telegram Login установлен на основном сервере; реальный вход подтверждается владельцем в обычном браузере.

Добавлены учебник из восьми тем с сохранением прогресса, светлая/тёмная тема и RU/EN интерфейс. По умолчанию используются настройки Telegram или браузера; ручной выбор хранится на устройстве. Язык интерфейса не меняет язык публикаций канала. Обновление тарифа повторно читает доступ, сохраняет черновики настроек и возвращает кнопку в рабочее состояние при сетевом таймауте.

Сервер получил `neyro-posting:billing-live-20261003`, затем уточнение клиента подключения
`neyro-posting:billing-live-20261003-r2`. В текущем состоянии `BILLING_ENABLED=0`,
`YOOKASSA_ENV=live`, `YOOKASSA_RECEIPT_MODE=npd_manual`, `YOOKASSA_FISCAL_READY=1`,
`BUSINESS_MODE_ENABLED=0`. Новый ключ сохранён в закрытом окружении; кабинет загружает
Telegram Login и меняет язык/тему. Успешный вход пользователя и оплата ещё не подтверждены.

Клиент допускает два дополнительных повтора только при ошибке установления соединения,
до передачи HTTP-запроса. Таймаут подключения — 5 с, остальных операций — 15 с.
Неясный результат после отправки не повторяется немедленно: сохраняется обычная сверка
того же заказа с тем же ключом идемпотентности. TLS и проверка имени сервера не ослаблены.
[Ограничения повторов HTTPX](https://www.python-httpx.org/advanced/transports/).

Повторы не устранили сетевую нестабильность: три из четырёх проверочных чтений магазина
прошли, одно завершилось таймаутом. До подтверждения связи оплату не включать.
