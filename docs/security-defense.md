# Защита сервиса: 2 октября 2026

> Актуальное состояние на 3 октября: основной домен flipbazar.ru; rate limiting, изоляция Docker и ограниченная роль БД применены. На резерве работают зашифрованные копии с проверкой восстановления и мониторинг. Внешняя Anti-DDoS и кандидат WAF не включены. Ниже сохранён первоначальный аудит и последующие обновления; текущую сводку и оставшиеся задачи см. в [HANDOFF.md](HANDOFF.md).

## Границы результата

Это усиление одного VPS, а не гарантия защиты от всех атак. Внешняя Anti-DDoS,
WAF, защищённый домен, VPN/MFA, внешние резервные копии и мониторинг требуют
отдельной инфраструктуры. До подключения фильтрации канал VPS можно перегрузить.

## Проверено непосредственно на VPS

- Около 2 ГБ RAM, swap 512 МБ; примерно 21 ГБ свободного диска.
- SSH: PasswordAuthentication no, KbdInteractiveAuthentication no;
  root допускается по ключу. Fail2ban активен.
- UFW активен; разрешены 22/80/443 для IPv4 и IPv6.
- Контейнеры не публикуют 5432 и 8080 на хосте.
- Таймер apt-daily-upgrade активен; результаты установки обновлений отдельно не проверены.
- Публичный адрес — технический sslip.io с IP в имени, не собственный домен.
- Контейнер Glances находится в restarting; его не изменяли.
- В systemd не обнаружен таймер резервного копирования приложения. Это не исключает
  наличие cron или копий у провайдера; восстановление не проверялось.

## Подготовленные изменения

- Перед авторизацией и чтением тела HTTP-запроса: token bucket 10 запросов/с на
  IP с запасом 60; общий бюджет 50/с с запасом 100; максимум 32 активных запроса.
  Все HTTP-пути, включая статику и healthz, участвуют в лимите. Ответы 429/503
  содержат Retry-After: 5. Это стартовые значения, не измеренная ёмкость VPS.
- IPv6 адреса одного /64 делят бюджет; IPv4-mapped IPv6 нормализуется.
  Заголовки не читаются лимитером. Только доверенный Caddy 172.30.90.2 может
  передать клиентский IP через Uvicorn. Caddy перезаписывает X-Forwarded-For.
- Память счётчиков ограничена 8192 адресами. При заполнении новые адреса получают
  отказ до освобождения неактивных записей, а действующие лимиты не вытесняются.
  Общий лимит и заполнение таблицы могут отказать честным пользователям во время
  атаки; задача — сохранить процесс, а внешняя фильтрация должна сохранить доступность.
- Старые пользовательские лимиты остаются отдельным уровнем. Новый IP-лимит
  разделяют люди за одним NAT. Счётчики локальны процессу и сбрасываются при рестарте;
  перед горизонтальным масштабированием нужен общий лимитер или edge enforcement.
- Caddy: заголовки до 32 КБ, получение заголовков до 5 с, тела до 15 с,
  idle 30 с; подключение к приложению до 3 с. Длительные AI-ответы не обрезаются
  новым таймаутом записи. Отдельного ограничения CPU парсинга это не даёт.
- Журнал запросов Caddy в stdout, без входящих заголовков, URI/query и заголовков
  ответа. IP и коды ответа остаются для расследования. Ротация Docker 3 × 10 МБ.
  Централизованного хранения и автоматического оповещения по этим логам пока нет.
- Раздельные сети: ingress (Caddy + app), database (app + support + db),
  отдельные исходящие сети для app/support/Caddy. Первые две internal.
  Caddy не состоит в сети БД; БД не получает внешнюю сеть.
  Это изоляция контейнерных сетей, не полноценная политика запрета каждого
  соединения: участники одной сети могут соединяться между собой.
- App/support: read-only root filesystem, отдельный ограниченный /tmp,
  cap_drop ALL, no-new-privileges. Сохраняется writable каталог данных приложения.
- Ограничения RAM: app 768 МБ, db 384 МБ, Caddy 192 МБ, support 128 МБ;
  PID: 128/128/128/64. CPU-квоты пока не установлены. Эти лимиты нужно наблюдать
  под реальной нагрузкой, особенно обработку изображений и OOM.

## Целевая внешняя архитектура

Интернет → Anti-DDoS L3/L4 + L7/WAF → Caddy → приложение → изолированная БД.
Администратор → VPN/ZTNA с MFA → отдельный административный доступ.
Журналы и зашифрованные резервные копии → отдельное хранилище вне VPS.

1. Установить провайдера, доступ в его панель, условия очистки трафика и бюджет.
   Технический адрес не доказывает, что включена Anti-DDoS у хостера.
2. Зарегистрировать/использовать собственный домен, включить MFA у регистратора,
   хостера и провайдера защиты. Не менять адрес Telegram Mini App до проверки TLS.
3. Подключить фильтрацию L3/L4 и WAF/L7. Проверить Telegram WebView: интерактивные
   CAPTCHA/JS challenge на API могут ломать приложение. Начать WAF с наблюдения,
   затем включать правила по результатам проверок. Не считать User-Agent Telegram
   подтверждением подлинности клиента.
4. После проверки прокси закрыть прямые 80/443 на origin: разрешать только ingress
   провайдера либо использовать исходящий туннель. Согласовать продление TLS.
   Сначала проверить резервную консоль и SSH, учесть IPv6 и Docker firewall.
   При необходимости заменить раскрытый IP. Не доверять произвольному XFF:
   при смене edge обновить доверенные прокси и проверку реального IP.
5. Настроить внешний uptime/TLS/DNS мониторинг, оповещения о 429/5xx, нагрузке,
   OOM, диске, ошибках входа и остановке бэкапов. Для отправки выбрать получателя.
6. Автоматизировать pg_dump + копии нужных медиа, шифрование и выгрузку вне VPS,
   неизменяемые версии/раздельные права удаления, пробное восстановление в
   изолированную БД без Telegram polling. Определить RPO/RTO с владельцем.
7. Выделить deploy-пользователя; docker group равна фактически root-доступу.
   MFA через VPN/ZTNA, резервные коды вне сервера; инвентаризация и отзыв SSH-ключей.
8. Разделить роль миграций БД и повседневную роль приложения; контейнер PostgreSQL
   по умолчанию создаёт POSTGRES_USER с расширенными правами. Проверить реально
   используемую роль перед миграцией прав.
9. В CI добавить сканирование зависимостей и образов, секретов, фиксацию digest
   образов, обновления с тестами. Пентест отдельно в согласованном окружении.
10. SIEM/EDR/IDS выбирать с учётом ресурсов; тяжёлое хранилище событий вынести
    за этот VPS. SOAR вводить после настройки сигналов, с обратимыми действиями.
    mTLS нужен при разнесении сервисов/прохождении недоверенной сети; на одном
    VPS сначала решаем внешнюю защиту, права и изоляцию. VLAN/VRF и NAC/802.1X
    относятся к управляемой сетевой инфраструктуре, которую VPS-проект не контролирует.

## При атаке

- Зафиксировать время, симптомы, коды ответа и показатели CPU/RAM/сети снаружи.
- Включать согласованные ограничения у провайдера фильтрации, связаться с хостером.
- Сохранить журналы вне VPS; не выводить токены/заголовки авторизации в отчёты.
- При подозрении на взлом ограничить доступ, сохранить доказательства, отозвать
  скомпрометированные ключи и восстанавливать чистое окружение.
- После стабилизации проверить очередь публикаций и доставку, исключить дубли;
  разобрать причины и обновить правила. Не перезапускать бесконечно под атакой.

## Статус применения

Полный локальный прогон: 368 тестов прошли на отдельной временной PostgreSQL.
Caddy и Compose прошли серверную проверку конфигурации; собранный образ прошёл
проверку авторизации и раннего ограничения запросов без доступа к рабочей сети.

Первая попытка переключения остановилась из-за конфликта IP в ingress:
Docker выдал динамический .2 приложению, тогда как .2 зарезервирован для Caddy.
Автоматический откат завершился, прежние контейнеры вернулись в рабочее состояние.
Локально исправлено: app получает статический 172.30.90.3, Caddy — 172.30.90.2.

Повторное применение после исправления не запускалось: автоматическая проверка
разрешений заблокировала SSH-команду из-за исчерпанного лимита использования.
Поэтому новое усиление НЕ считать включённым на рабочем сервере.
Последнее подтверждённое состояние — прежняя рабочая версия после отката.

Резервная копия перед попыткой: /opt/neyro-security-backups/20261002T131151Z
на сервере (дамп БД, список содержимого дампа, прежние конфиги и код).
Проверка списка дампа не заменяет полноценного пробного восстановления.

Для завершения: повторить проверку конфигурации и адресов, применить исправленные
файлы с резервированием и откатом, проверить внешний HTTPS, 401/429 через Caddy,
защиту от подделки X-Forwarded-For, отсутствие чувствительных полей в access log,
ресурсные ограничения и связи контейнеров. До этого не заявлять готовность защиты.

## Обновление фактического состояния после продолжения

Следующие результаты заменяют прежний раздел «Статус применения»:

- Исправленная защита применена на основном VPS. Проверены HTTPS 200,
  неавторизованные 401 и превышение лимитов 429 (17 отказов в ограниченной серии
  80 обращений); меняющиеся поддельные XFF не обошли ограничение.
- Подтверждены отдельные Docker-сети, read-only app/support, cap_drop ALL,
  no-new-privileges и лимиты памяти/PID. Лимит support увеличен до 256 МиБ
  после достижения первоначальных 128 МиБ, без OOM на момент измерения.
- flipbazar.ru и www добавлены в Caddy, сертификат HTTPS проверен с резерва;
  https://flipbazar.ru/healthz вернул {"ok":true}. Прежний sslip.io адрес оставлен.
  PUBLIC_URL приложения заменён на https://flipbazar.ru при смене DB-роли.
- Создана отдельная ограниченная роль neyro_app, ей передано владение таблицами
  и последовательностями. Приложение/поддержка переключены на неё; admin-пароль
  БД исключён из их env_file (.app.env). Суперпользователь bootstrap neyro
  сохранён только для администрирования БД: PostgreSQL запрещает снять у него
  superuser. Роль приложения всё ещё владеет схемой данных для startup migrations;
  полное разделение DDL и DML не выполнено.
- Резервный VPS 144.31.53.148 настроен: ключевой SSH, парольный SSH выключен,
  исходный пароль заменён, Fail2ban/UFW/таймер автообновлений; наружу только 22.
- Зашифрованные off-host копии каждые 15 минут, ротация 7 дней, каждую проверяет
  реальное восстановление в disposable PostgreSQL без сети. Первый результат:
  9 пользователей, 14 каналов, 2842 поста. На резерве восстановлена БД,
  рабочие боты и публичный прокси не запущены.
- Мониторинг с резервного VPS каждую минуту, контроль возраста копии.
  Токен для уведомлений перенесён с отдельного разрешения пользователя;
  тестовое уведомление администраторам доставлено. Улучшенная версия alert-state
  по каждому получателю пока только локальна.

Ещё не выполнено: WAF-кандидат не прошёл end-to-end тесты и не развёрнут;
refresh-standby.sh, новый экспорт .app.env/образа прокси, исправление прав data
и персональная доставка алертов пока локальны. Нет полного пробного failover,
внешнего WAF, подтверждения условий Anti-DDoS для локаций, MFA/VPN, третьей
независимой площадки и завершённого vulnerability scan/pentest.

Автоматическая проверка разрешений вновь заблокировала SSH из-за лимита
использования. Последняя read-only попытка подключения не запускалась.
Локально проверено: 66 тестов auth/ingress/safe_http/alerts прошли; бинарник
WAF собран и конфигурация проходит Caddy adapt --validate. Сетевые WAF-тесты
не стартовали из-за ограничения bind к loopback в sandbox — это не успех тестов.

Подробный безопасный порядок восстановления: docs/disaster-recovery.md.

compose не включает её, пока поведение не проверено.
