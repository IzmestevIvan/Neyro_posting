## CI

`.github/workflows/ci.yml` запускается на main, ветках `codex/**`, pull request и вручную.
Задания работают на временных GitHub-hosted Ubuntu runners, без рабочих секретов:

- **Backend**: PostgreSQL 16 на localhost, только база `neyro_test`, Python 3.12,
  настоящий набор тестов. `PYTHON_DOTENV_DISABLED=1` предотвращает чтение `.env`.
- **Frontend**: четыре JS-suite и семь браузерных suite; снимки отдельно по сценарию.
- **Infrastructure**: проверка секретов/версий, тесты выпуска и отката, синтаксис
  Ansible, ограничения workflow, Kustomize и Kubernetes schema validation.
- **Container**: сборка Dockerfile, проверка UID 10001 и импортов без сети/worker,
  инвентарь установленных Python-пакетов (`pip inspect`). Это инвентарь, не полный
  SBOM всех пакетов ОС и не сканер всех уязвимостей контейнера.

CodeQL вынесен в отдельный workflow, запускается на PR/main и еженедельно.
Dependabot еженедельно предлагает изменения; автоматического merge нет.
Нельзя объединять только по наличию предложенного обновления — нужны проверки.
Actions закреплены за SHA. Права по умолчанию только чтение. У PR нет доступа
к production Environment; `pull_request_target` и собственный runner на VPS не используются.
[Рекомендации GitHub](https://docs.github.com/en/actions/reference/security/secure-use).

`requirements.lock` содержит фактические версии runtime рабочего образа до изменений,
включая транзитивные зависимости. При изменении `requirements.txt` нужно обновить lock
и проверить чистую сборку. Lock закрепляет версии, но не содержит хешей каждого wheel.
Dockerfile использует digest официального Python 3.12 slim. Старый работающий контейнер
не пересобирается автоматически от правки Dockerfile в рабочей папке.

## Выпуск

Порядок: ветка → PR → CI → main → CI на main → **Deploy production / Run workflow**.
Для владельца-одиночки требуемые проверки и PR включаются без обязательного чужого
approval; владелец не может одобрить свой PR. Защита запрещает force push и удаление main.

`deploy.sh` теперь только вызывает workflow через GitHub CLI и не загружает рабочую
папку. Workflow берёт собственный код из main, требует полный SHA, текущую вершину main
и успешный push-прогон CI этого SHA. Любые незакоммиченные файлы исключены из пакета.

Сервер получает пакет через отдельный SSH-ключ с forced command и `restrict`:
разрешены только upload/deploy/status. Нет shell, forwarding и произвольного SCP.
Хост сверяется с заранее проверенным known_hosts; автоматического доверия новой
подписи нет. Секреты ботов, платежей, БД и общий административный SSH-ключ не передаются
в GitHub. Деплойный ключ хранится только в закрытом локальном файле и GitHub Environment.

Root-owned серверный worker дополнительно проверяет текущий main, успешный CI и
сравнивает все файлы загрузки с архивом того же SHA из фиксированного GitHub-репозитория.
Это требует доступности GitHub с VPS; при сбое запросов выпуск остановится до изменений.
Поскольку репозиторий публичный, токен GitHub на VPS не нужен. Если сделать его приватным,
нужно отдельно пересмотреть механизм чтения доверенных исходников.

Перед обновлением:

1. Проверяются пути и SHA-256 всех файлов. Ссылки, выход из каталога, дубликаты,
   переменные окружения и большие загрузки отклоняются.
2. Сверяются `app/db.py` и `app/billing/schema.py` с работающим кодом. Изменения схемы
   требуют отдельного выпуска с планом миграции; автоматический путь их блокирует.
3. Сохраняются предыдущие файлы и ID **обоих** образов app/support, создаётся
   зашифрованный снимок штатным экспортёром. Экспорт проверяет структуру дампа;
   полная проверка восстановления делается резервом, не самим CD.
4. Новый образ собирается с SHA-тегом и проверяется без сети/публикаций.
5. Под блокировкой экспорта снимков обновляются только app и support. База и Caddy
   не перезапускаются. `.env`, `.app.env` и `.support.env` не меняются; в частности,
   CD не включает оплату и не добавляет новые настройки окружения автоматически.
6. Проверяются Docker health и публичный HTTPS `/healthz`. При ошибке возвращаются
   предыдущий код и точные образы app/support. База не откатывается автоматически:
   после снимка могли появиться новые публикации или платежи.

Возможен короткий перерыв при замене единственного worker; это не zero-downtime.
GitHub хранит только безопасный статус. Полные серверные build-логи закрыты:
`/var/log/neyro-deploy/<sha>.log`. Статус — `/var/lib/neyro-deploy/status/<sha>.json`,
текущая версия — `current.json`, откат — каталог `/opt/neyro/backups/ci-…`.
При неясном результате сначала посмотреть статус, затем решать о повторе. Новый SHA
требуется после неудачи с уже созданным release-каталогом. Независимая команда изменения
Caddy/Compose/секретов остаётся административной операцией, CD их не разворачивает.

## Ansible

Инвентарь — `infra/ansible/inventory.yml`, ключ администратора берётся из существующего
`~/.ssh/neyro_deploy`. Пароли в Git не добавляются. Playbook предназначен для **текущих**
Ubuntu 24.04 с уже установленным Docker и восстановленным приложением; он не заявлен
как установка продукта на пустой VPS.

```sh
make ansible-check   # --check --diff, предварительная проверка
make ansible-apply   # применить только после проверки diff
```

Кроме SSH, обновлений и закрытых env-файлов, Ansible управляет UFW и Docker ingress,
Fail2ban, аудитом, ограничением журналов, резервными таймерами и мониторингом.
Операционные процедуры выполняются через `operations.yml`; детали, ограничения
восстановления и команды — в [server-orchestration.md](server-orchestration.md).
DNS и рабочая БД не меняются обычным `site.yml`.

## Подключение нового окружения (справочная последовательность)

1. Проверить diff и сохранить локальные файлы в ветке, отправить PR. Дождаться всех
   CI-задач, исправить реальные ошибки Linux/чистой сборки. Только затем объединить.
2. Выполнить `python3 scripts/ci/configure_github.py baseline` через авторизованный
   GitHub CLI. Скрипт включает scanning, push protection, alerts, приватные отчёты,
   read-only Actions и Environment production. Предыдущие успешные операции не
   откатываются при ошибке следующего API-запроса — сверить фактическое состояние.
3. После зелёного CI на main выполнить `python3 scripts/ci/configure_github.py protect-main`.
   Он откажется включать обязательные проверки до успешного CI текущей вершины.
4. Создать отдельный Ed25519-ключ выпуска в игнорируемом закрытом каталоге; не
   переиспользовать административный ключ. Применить Ansible сначала `--check --diff`,
   затем обычно с `-e ci_public_key_file=/абсолютный/путь/к/ключу.pub`.
5. В Environment **production** записать секрет `DEPLOY_SSH_KEY`, переменные
   `DEPLOY_HOST=31.76.244.26`, `DEPLOY_KNOWN_HOSTS` с проверенной подписью этого сервера.
   Пример передачи ключа без вывода: `gh secret set DEPLOY_SSH_KEY --env production < /закрытый/ключ`.
   Host key сверять с уже доверенным SSH/консолью, а не принимать слепой ssh-keyscan.
6. Проверить forced command: произвольный shell должен отклоняться, status — работать.
7. Запустить один контролируемый Deploy production для текущего main. Проверить
   рабочую версию, `/healthz`, сохранение `BILLING_ENABLED=0` и отсутствие дубля worker.
8. Запустить штатное копирование резервом, убедиться в восстановлении и проверить
   повторный Ansible-прогон на отсутствие неожиданных изменений. Обновить HANDOFF
   фактическими результатами, ID CI/CD run и коммитом.

## Локальная проверка и ограничения

До изменения инфраструктуры полный набор дал **600 passed, 8 skipped** (WAF).
После добавления: **9** изолированных unit-тестов выпуска/отката и **4** JS-suite прошли;
синтаксис Ansible, инвентарь, проверки workflow/секретов/версий также прошли.
Новые тесты не вызывают SSH/Docker и не меняют рабочую базу. GitHub CI, чистая сборка контейнера и Kubernetes schema validation прошли.
Результат контролируемого реального CD записывается в HANDOFF и GitHub Actions.

```sh
make check
make test-ui
python3 -m unittest tests.test_release_tooling -v
# PostgreSQL только локальная тестовая БД:
TEST_DATABASE_URL=postgresql://neyro@127.0.0.1:55439/neyro_test make test
# После npm ci и установки Chromium:
make test-browser
```

`make hooks` включает локальный pre-commit (проверки пробелов, секретов и lock);
CI повторяет проверки независимо от наличия hook. Это эвристики известных шаблонов,
не доказательство отсутствия любого возможного секрета. GitHub secret scanning
должен быть включён отдельно; после обнаружения ключ нужно отозвать у провайдера.

Kubernetes и условия переноса: [infra/kubernetes/README.md](../infra/kubernetes/README.md).
Ещё не реализованы внешний Anti-DDoS, автоматическое аварийное переключение, отдельная
staging-среда, внешний сборщик метрик/логов и полный скан контейнеров. Их нельзя считать
готовыми только из-за наличия CI/CD. [Защита](security-defense.md), [резерв](disaster-recovery.md).
